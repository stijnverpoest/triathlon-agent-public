Core idea

Reason in prompts, execute in Python, persist everything as files.

The repo deliberately splits coaching reasoning from execution and write-back. The LLM side decides what the week should be. The Python side fetches data, normalizes context, validates artifacts, compiles workouts, and pushes only after approval.

Operator notes
  • Open with any modern browser.
  • Use arrow keys, space, Page Up or Page Down.
  • Everything is self-contained in one HTML file.
  • No secrets or athlete-specific local files are embedded here.

Why This Exists

The planning problem is half data pipeline, half coaching judgment.

A useful weekly plan is not just a prompt response. It has to combine live training data, subjective athlete context, constraints, doctrine, and safe write-back.

Constraints the system has to satisfy
  • Use fresh Intervals.icu activities, wellness, sport settings, and race calendar.
  • Ask only for things the API cannot know, such as pain, travel, and availability.
  • Make the reasoning inspectable after the fact.
  • Be safe enough to push structured workouts into a real training calendar.
  • Support offline, deterministic testing without credentials.
Why not one monolithic prompt?
  • Different decisions have different objectives: readiness, macro phase, race specificity, weekly layout, doctrine, nutrition, and validation.
  • Ordered agent outputs are easier to validate than one giant freeform answer.
  • Persisted JSON artifacts make the run resumable, reviewable, and testable.
  • Python remains deterministic for fetch, compile, validation, and push.
Design target: practical weekly planning with an auditable trail README.md · DESIGN.md
System Architecture

Two-layer architecture with a hard boundary at run artifacts.

The agent layer owns coaching reasoning. The Python layer owns deterministic preparation, validation, compilation, and write-back.

High-level flow

The run folder is the state boundary. The LLM layer writes artifacts into it. The Python layer validates and pushes from it.

Public-safe architecture choices
  • Standard library Python only.
  • Local-only athlete data and `.env` stay out of git.
  • `runs/` acts as a complete audit log for each planning session.
  • Reasoning is externalized into prompts and persisted outputs, not buried in one opaque runtime.

End-to-End Workflow

From “plan my week” to approved Intervals events.

The production flow always starts with fresh data fetch and stops at an approval gate before any write-back.

1
User request
The user says plan my week. The CLI rewrites the phrase to prepare-run rather than drafting immediately.
2
Prepare run
Fetch Intervals profile, sport settings, wellness, activities, and calendar events. Load local athlete profile and weekly check-in.
3
Normalize snapshot
Write normalized_snapshot.json and run_context.json so the main agent can reason over one coherent view.
4
Targeted follow-up
Summarize what happened last week, then ask only for subjective feedback and next-week constraints the API cannot know.
5
Specialist chain
Run agents in order, writing one JSON artifact per role into agent_outputs/.
6
Finalize
Validate contracts, aggregate outputs, render weekly_report.md, and keep approval status pending.
7
Approval gate
A human reviews the report. No compilation and no push happen before approval.
8
Compile and push
Compile workouts and note events, run the syntax guard, bulk upsert to Intervals, and record push_result.json.
Production command sequence 
python3 -m triathlon_agent.cli prepare-run \
  --mode live \
  --athlete-profile data/athlete_profile.json \
  --weekly-checkin data/weekly_checkin.json

python3 -m triathlon_agent.cli finalize-run runs/<run_id>

python3 -m triathlon_agent.cli approve runs/<run_id> --mode live

The deterministic stub flow still exists for tests and offline demos, but live planning is intentionally staged through prepare-run and finalize-run.

Mandatory order is documented in prompts/weekly_workflow.md prepare-run -> finalize-run -> approve
Specialist Agents I

Diagnosis, macro direction, race lens, and week layout.

The first half of the chain turns raw athlete context into a draft seven-day training week.

1

performance_doctor

Reads readiness, fatigue, recovery, and injury risk from live history plus subjective check-in. Sets the caution level for the week.

readinessfatiguerisk
2

macro_coach

Applies Friel-style periodization to classify the week, determine phase, and decide whether the athlete should load, absorb, recover, or taper.

3

race_director

Chooses the priority race lens from Intervals calendar data and translates it into race-specific needs for this week.

race priorityspecificitycalendar-aware
4

head_coach_planner

Builds the seven-day schedule. Places workouts, recovery, session durations, and discipline-specific targeting while respecting constraints.

DanielsCogganweekly layout
These four agents create the initial coaching shape of the week performance -> macro -> race -> plan
Specialist Agents II

Audit, critique, fueling, synthesis, and pre-push safety.

The second half of the chain treats the draft like code review: phase alignment, doctrine checks, realism checks, then delivery formatting.

5

phase_alignment_auditor

Checks whether the drafted week matches the macro phase and the race timeline. Flags plans that are too aggressive or mistimed.

6

training_philosophy_auditor

Verifies doctrinal coherence across Daniels for runs, Coggan for bikes, and Friel for block structure.

7

validator_coach

Acts as quality control. Critiques overload, sequencing, realism, and unnecessary complexity. Proposes edits before the plan is finalized.

8

nutritionist

Maps fueling and hydration guidance onto the actual plan and produces only meaningful daily note events.

9

orchestrator

The synthesis layer. Resolves conflicts across specialists and writes the final narrative package as final_plan.json.

post-approval

intervals_syntax_guard

Runs only after approval. Reviews compiled workout descriptions for Intervals parseability and rewrites syntax conservatively without redesigning the plan.

Reasoning ends at final_plan.json; syntax guard operates only on compiled payloads auditors + validator + nutrition + synthesis
Contracts And Artifacts

This system reasons through files, not just chat.

Prompts define roles. Schemas define output shape. The run folder becomes the complete, inspectable state of a planning session.

Typical run folder
runs/<run_id>/ inputs.json normalized_snapshot.json run_context.json planning_state.json approval.json draft_plan.json final_plan.json weekly_report.md athlete_brief.md agent_outputs/ performance_doctor.json macro_coach.json race_director.json head_coach_planner.json phase_alignment_auditor.json training_philosophy_auditor.json validator_coach.json nutritionist.json compiled_workouts.json compiled_notes.json compiled_push_payload.json push_result.json
Why this matters
  • prompts/*.md hold the reasoning instructions for each role.
  • schemas/*.json define the required shape for each specialist output.
  • contracts.py re-validates those contracts locally before the report is treated as final.
  • The artifact trail makes debugging and public explanation much easier.

Python Tooling Layer

The modules are intentionally small, explicit, and boring.

The Python side does not try to be the coach in production. It provides stable rails around the coaching workflow.

cli.py

Exposes prepare-run, finalize-run, approve, and mock-only plan-week. Also rewrites plan my week to prepare-run.

workflow.py

Owns run-folder lifecycle, state transitions, artifact writes, validation hooks, and final push orchestration.

normalizer.py

Merges local inputs, Intervals data, race data, adherence history, wellness, and constraints into one planning snapshot.

intervals.py

Provides live and mock adapters. Live mode uses stdlib urllib; mock mode returns fixture-backed responses.

compiler.py

Converts the approved plan into Intervals-compatible workout events and note events, preserving conservative syntax.

report.py

Renders weekly_report.md and athlete_brief.md for human review before push.

contracts.py

Validates specialist outputs and final plan structure, including doctrine-specific fields like Daniels type or Coggan IF and TSS.

Execution rails instead of hidden magic standard library Python only

Modes And Safety

Mock mode keeps tests deterministic. Live mode keeps write-back gated.

The repo is designed to support both public demonstration and real athlete use without collapsing those two concerns into one unsafe path.

Mock mode
  • Uses fixture-backed Intervals snapshots.
  • Supports plan-week --mode mock for deterministic dry-runs.
  • Makes tests stable and public demos reproducible.
  • Returns fake push results instead of touching a real account.
Live mode
  • Uses a personal API key from local .env.
  • Starts with a fresh fetch through prepare-run.
  • Waits for explicit approval before any compile or push step.
  • Records exact push payload and push result back into the run folder.
Approval gate
  • approval.json begins in pending.
  • finalize-run renders the human review package.
  • approve compiles and pushes only after approval is recorded.
Pre-push protections
  • Local contract validation through contracts.py.
  • Conservative workout syntax generation in compiler.py.
  • intervals_syntax_guard checks payload parseability after approval.
No direct push from prompt reasoning approval.json -> compiled_push_payload.json -> push_result.json
Write-Back Model

What actually gets pushed after approval.

The final plan is not pushed raw. It is compiled into Intervals event payloads with a conservative mapping by discipline and session type.

Compilation rules
  • Bike workouts target %FTP.
  • Easy or aerobic runs target HR.
  • Quality runs target Pace from Intervals threshold pace.
  • Swims are pushed as simple swim events when structure does not need full syntax.
  • Strength is represented conservatively as structured notes.
  • Recovery sessions are not blindly pushed as workouts.
Push outputs
  • compiled_workouts.json - structured workout events
  • compiled_notes.json - nutrition or focus notes
  • compiled_push_payload.json - exact payload about to be sent
  • push_result.json - exact response from Intervals

This keeps the calendar write-back deterministic and auditable even though the weekly reasoning itself comes from specialist prompts.

Approved plan -> compiled events -> syntax guard -> Intervals bulk upsert compiler.py + intervals.py
Operator Commands

The user-facing surface is intentionally small.

Most of the architecture complexity is behind three main commands and one fixture-only convenience path.

Live production path 
python3 -m triathlon_agent.cli prepare-run \
  --mode live \
  --athlete-profile data/athlete_profile.json \
  --weekly-checkin data/weekly_checkin.json

python3 -m triathlon_agent.cli finalize-run runs/<run_id>

python3 -m triathlon_agent.cli approve runs/<run_id> --mode live
Command semantics
  • prepare-run fetches and normalizes data, then creates the run shell.
  • finalize-run validates specialist outputs and renders the report and athlete brief.
  • approve compiles and pushes after approval.
  • plan-week exists for deterministic mock runs and tests, not for live production reasoning.
Fixture-backed dry run 
python3 -m triathlon_agent.cli plan-week \
  --mode mock \
  --athlete-profile fixtures/athlete_profile.json \
  --weekly-checkin fixtures/weekly_checkin.json
Important nuance

The phrase plan my week intentionally resolves to prepare-run, not to direct drafting. That design forces the system to fetch live data and ask the required post-fetch questions first.

Tradeoffs

Strengths and limitations of the design.

The repo optimizes for inspectability and safe execution, not for maximal runtime abstraction.

What works well
  • Clear separation between reasoning and execution.
  • Inspectable, resumable run artifacts.
  • Mock and live parity for safer development.
  • Human approval before any calendar mutation.
  • Public-friendly repository shape with local-only secrets and athlete data excluded.
Known limitations
  • The agent prompt-call loop is documented rather than fully embedded inside the CLI.
  • Swim structure is lighter than bike or run structure.
  • Strength handling is intentionally conservative.
  • The architecture is explicit and file-heavy by design, which means more visible moving parts.
Bias: boring execution, explicit state, inspectable decisions DESIGN.md known limitations
Closing

The repo is really a controlled interface between LLM reasoning and a real athlete calendar.

The point is not “AI writes a week”. The point is that a coaching workflow can be structured, validated, reviewed, and pushed with the same discipline we expect from technical systems.

Takeaway

Prompt engineering alone is not the architecture.

The architecture is the combination of prompts, contracts, deterministic tooling, artifacts, approval, and a write-back layer that can be trusted enough to touch a real external system.

Fresh data in. Specialist reasoning through files. Human approval. Deterministic push out.
